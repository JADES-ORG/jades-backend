# Verificación previa al PR de JADES

Revisión del 21 de noviembre de 2026 sobre el commit 61dbf5c de la rama de auditoría.

- El enunciado SI642, caso de cuenta corriente, exige cuota francesa, capitalización de la gracia, control del límite, intereses hasta el pago y rechazo de pagos parciales. El informe del equipo excluye expresamente el adelanto de cuotas. El backend rechaza fechas anteriores al vencimiento y conserva la imputación de capital, interés y mora.
- Las clases de tasas nominales, efectivas y planes de pago sustentan convertir el período antes de capitalizar. No determinan la representación numérica de la API. El informe describe porcentajes y el manual técnico usa fracciones. El motor heredado acepta tanto 18 como 0.18 para el 18 % y lee 0.5 como 50 %. Falta acordar una unidad explícita con el frontend y un tratamiento de datos previos antes de cambiar esa interpretación.
- El límite se controla primero sobre la compra y después sobre el saldo que incluye la gracia capitalizada. El enunciado exige el límite y la capitalización, pero no precisa si la gracia consume línea. Se conserva ese criterio y se prueba con precio igual al límite.
- Se consultan los valores originales guardados, aun si falta el pacto completo. Una tasa histórica desconocida se devuelve nula. Si es indispensable para liquidar mora vencida, se devuelve conflicto. Un pago registrado conserva sus importes reales. Los endpoints de generación para una venta existente consultan la obligación que se creó al registrar la venta. Las ventas antiguas sin obligación requieren conciliación documental.
- El listado determina el ciclo de cada cuota con su propio pacto. Para créditos antiguos usa el vencimiento y, cuando necesita distinguir meses consecutivos, el corte y primer pago guardados. Si falta ese calendario devuelve conflicto. Cuando concurren distintos vencimientos del ciclo, la fecha de pago común es nula. El detalle mantiene la fecha de cada cuota. Las cabeceras de corte y las ventas antiguas sin corte asignado todavía dependen del calendario vigente.
- El alta solicita correo y contrasenaTemporal, coherente con el campo de Figma. En jades-frontend/main (93d3f69), App.tsx contiene la plantilla de Vite y no implementa el alta. El cliente API usa VITE_API_URL o localhost:8080 y envía Bearer. Se admite localhost:5173 para desarrollo y un origen explícito de despliegue mediante JADES_FRONTEND_ORIGIN. Queda pendiente la prueba en navegador con el formulario implementado y el tratamiento de valores históricos nulos en los tipos TypeScript.
- Al actualizar el correo de un cliente con acceso, el backend valida longitud, normaliza el correo y actualiza el usuario en la misma transacción. Una tienda inactiva admite consultas financieras y cobros por el administrador que conserva su vínculo activo. Registrar nuevas ventas sigue requiriendo tienda activa.
- La migración docs/credito_condiciones_aplicadas.sql se ejecutó dos veces en PostgreSQL 16.4 sobre un clúster temporal creado con initdb. Se usó una tabla credito de prueba con una fila previa (id 17, saldo 125.50). Ambas ejecuciones terminaron correctamente, quedaron 14 columnas nuevas, el saldo se conservó y la tasa histórica siguió en NULL. La prueba cubre el ALTER TABLE y su repetición, no una copia completa del esquema productivo.

Maven 3.10.0, JDK 21 y H2 en memoria para integración. El comando mvnw -o test con el agente Mockito precargado terminó con BUILD SUCCESS en 8,100 s. Se ejecutaron 43 pruebas, 0 fallos, 0 errores y 0 omitidas. Incluye ambas modalidades, cambio de correo, consulta y cobro tras baja, rechazo del anticipo y exceso del límite por la gracia. PostgreSQL se probó separadamente para la migración.
